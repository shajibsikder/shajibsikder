Distributed Caching Patterns with Redis: Mitigating Cache Stampedes

When a high-traffic cache key expires, hundreds of application threads simultaneously miss the cache and hit the underlying database. Here is how to implement Redis atomic locks and TTL jitter to prevent system collapse.

Md Shajib Sikder

Backend Systems Engineer & Architecture Specialist

1. Understanding the Cache Stampede (Thundering Herd)

A Cache Stampede occurs when a heavily requested cached item (such as a news portal home payload or live scoreboard) expires. Suddenly, 500 concurrent HTTP requests simultaneously execute the heavy SQL query to re-populate Redis. The database CPU spikes to 100%, leading to cascaded connection timeouts.

2. Redis Mutex (Distributed Lock) Solution

Instead of allowing every request thread to query MySQL, we use Redis's atomic SET key value NX PX ttl command. Only the single thread that acquires the lock gets to execute the database query. 

// PHP / Redis Cache-With-Lock Pattern
public function getCachedData(string $key, callable $fallback, int $ttl = 300)
{
    $cached = Redis::get($key);
    if ($cached !== null) {
        return json_decode($cached, true);
    }

    $lockKey = "lock:{$key}";
    $lockAcquired = Redis::set($lockKey, "1", "NX", "PX", 5000); // 5 sec lock timeout

    if ($lockAcquired) {
        try {
            $freshData = $fallback(); // Execute heavy database query once
            Redis::setex($key, $ttl, json_encode($freshData));
            return $freshData;
        } finally {
            Redis::del($lockKey);
        }
    }

    // Secondary requests wait 50ms and retry reading the fresh cache
    usleep(50000);
    return json_decode(Redis::get($key), true);
}

3. TTL Jittering & Probabilistic Expiration

If 1,000 keys are cached at the exact same second with a static 60-minute TTL, they will all expire simultaneously 1 hour later. Introducing random TTL jitter spreads out expiration times naturally: 

// Calculate TTL with ±10% random jitter
$baseTtl = 3600; 
$jitter = rand(-360, 360);
$finalTtl = $baseTtl + $jitter;

Redis::setex($key, $finalTtl, $data);

Key Takeaways

  • Always wrap heavy database queries in an atomic Redis distributed lock.
  • Add 10% random TTL jitter to prevent synchronized key expirations.
  • Maintain a 90%+ Redis cache hit rate to safeguard database instance CPUs.
