Composite Database Indexing: Eliminating Table Scans in High-Concurrency APIs

Adding single-column indexes on every field in your table is an anti-pattern. Understanding how B-Tree composite indexes function under the hood allows you to write high-performance database schemas.

Md Shajib Sikder

Backend Systems Engineer & Architecture Specialist

1. The Leftmost Prefix Rule

A B-Tree composite index on columns (A, B, C) acts like a telephone directory ordered first by Last Name (A), then First Name (B), then Middle Name (C). MySQL can evaluate:

  • Queries matching (A)
  • Queries matching (A, B)
  • Queries matching (A, B, C)

However, a query matching only (B) or (B, C) cannot use the index!

2. Rule of Column Ordering: Equality vs Range

Always place exact equality columns (WHERE status = 'active') before range comparison columns (WHERE price > 100). 

-- CORRECT INDEX ORDER:
-- Column 1: status (Equality check)
-- Column 2: category_id (Equality check)
-- Column 3: created_at (Range / ORDER BY)
CREATE INDEX idx_orders_optimal ON orders (status, category_id, created_at DESC);

3. Managing Index Overhead & Write Amplification

Every index created requires disk I/O during INSERT, UPDATE, and DELETE operations because B-Tree leaves must re-balance. Aim to maintain 3 to 6 high-selectivity composite indexes per table rather than 15 single-column indexes.
