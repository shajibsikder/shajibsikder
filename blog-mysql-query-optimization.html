Optimizing High-Throughput MySQL Queries for Sub-10ms Latency

When scaling database-backed web applications to thousands of requests per second, database query latency quickly becomes your main bottleneck. Here is how we systematically diagnose and optimize slow MySQL queries.

Md Shajib Sikder

Backend Systems Engineer & Architecture Specialist

1. Diagnosing Slow Queries with EXPLAIN FORMAT=JSON

The first step in resolving database performance bottlenecks is understanding MySQL's query execution planner. Running a plain EXPLAIN gives basic table join information, but using EXPLAIN FORMAT=JSON exposes exact row estimates, evaluated condition costs, and temporary table usage. 

EXPLAIN FORMAT=JSON 
SELECT p.id, p.title, p.created_at, c.name AS category_name
FROM articles p
INNER JOIN categories c ON p.category_id = c.id
WHERE p.status = 'published' AND p.created_at >= '2026-01-01'
ORDER BY p.created_at DESC 
LIMIT 20;

Look out for two critical flags in the JSON execution breakdown:

  • "using_temporary_table": true — Indicates MySQL is allocating RAM or disk tables to process intermediate joins.
  • "using_filesort": true — Means MySQL could not use an index to satisfy the ORDER BY clause.

2. Building Covering Indexes

A covering index is an index that includes all of the fields requested by the query. When MySQL finds a covering index, it resolves the entire query directly out of the B-Tree memory space without performing expensive primary key disk lookups (bookmark lookups). 

-- Composite Index covering filter (status, created_at) and payload (category_id, title)
CREATE INDEX idx_articles_perf 
ON articles (status, created_at DESC, category_id, id);

By placing the equality column (status) first, followed by the range column (created_at DESC), MySQL can perform a direct index range scan and avoid filesorts altogether.

3. InnoDB Buffer Pool & Memory Optimization

Hardware configuration plays a pivotal role in maintaining sub-10ms response times under high concurrency. Ensure that your innodb_buffer_pool_size is set appropriately (typically 65% to 75% of available RAM on dedicated database instances). 

[mysqld]
# Allocate 8GB Buffer Pool split across 8 instances for low thread contention
innodb_buffer_pool_size = 8G
innodb_buffer_pool_instances = 8

# Reduce disk flush operations
innodb_flush_log_at_trx_commit = 2
innodb_io_capacity = 2000

Summary Benchmark Results

380ms Before (Table Scan)
6.4ms After (Covering Index)
59x Throughput Increase

Systematic query optimization combined with proper index positioning guarantees that your backend APIs remain responsive even during sudden traffic spikes.
